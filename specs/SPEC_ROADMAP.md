## Next Recommended Specs

- Live Stripe verification once a real Stripe account and test-mode API keys exist (`041-back-billing-foundation` shipped with `BILLING_PROVIDER=mock`; `StripeBillingProvider` is implemented but unverified against a live account).
- Migrate the 4 remaining fat routers (`users.py`, `devices.py`, `google_oauth.py`, `health.py`) into real `app/modules/` packages — `066-back-production-readiness-hardening`'s audit confirmed none have functional debt, purely structural consistency; `google_oauth.py` (130 lines) is the one actually worth the effort, the other three are trivial either way.
- Structured logging (Python's `logging` module) around auth failures, billing/payment paths, and other high-value spots — `066-back-production-readiness-hardening`'s audit found zero usage anywhere in `app/`; the app currently relies entirely on uvicorn's default access logs, which will hurt production incident response.
- ~~Numeric aggregation/trend-charting of check-in answers~~ Shipped as `nutri_pro`'s `074-front-checkin-numeric-trends` — no backend change needed: `CheckinField.type` already distinguishes `number`/`scale` fields, so the client parses those specific answers' already-string values and charts them, deliberately leaving `044-back-checkin-forms`'s string-only storage untouched.
- ~~Numeric rollups over logged workout exercises (total volume, 1RM tracking)~~ Deliberately out of scope for `045-back-workout-plans`'s v1 as a *backend* rollup, and it turned out none was needed: `nutri_pro`'s `058-front-workout-volume-and-1rm` computes these client-side; `073-front-workout-volume-trend` extended volume across a patient's full history (`GET /patients/{id}/workout-logs` was already unfiltered by plan); `075-front-historical-one-rep-max-trend` closes the harder 1RM half by fetching every historical `WorkoutPlan` a patient's logs reference (via the existing `GET /workout-plans/{id}`) and joining by exercise name across them.
- `065-back-dashboard-appointment-revenue-trend` adds `completed_appointments_by_month` and `estimated_revenue_by_month` to `GET /patients/dashboard`, closing "appointment/revenue trends still not built" from `048-back-practice-dashboard`'s note — revenue stays an estimate (session price × completed count), not real payment data, so it needed no Stripe/billing dependency at all. `066-back-production-readiness-hardening` is a dedicated pre-launch security pass (three parallel audit forks, one per repo): fixes an upload content-type-spoofing stored-XSS vector, adds missing size limits to 5 upload endpoints, applies rate limiting to `/auth/login`/`/auth/forgot-password`, makes `CORS_ORIGINS` fail-closed outside local dev, adds a missing ownership check on the messaging-attachment upload, and corrects `docs/modules/architecture.md`'s stale migration-progress claim (17/21 modules, not 5). Next steps are user-driven from here.
- ~~Session photos on a logged workout entry~~ Shipped as `062-back-workout-log-session-photo` (`photo_url`/`photo_content_type` on the per-exercise `workout_logs` document, plus a dedicated `POST /me/workout-logs/photo` upload endpoint mirroring `POST /me/messages/attachment`'s upload-then-reference shape).
- ~~Fix the seed/guardrail role mismatch found while verifying `062`~~ Fixed: `app/scripts/seed_dev.py` now seeds the demo nutritionist with `role="nutritionist"` (was `"pro"`, which `require_role("nutritionist")` — added later, in `040-back-tenant-isolation-hardening` — rejected); the already-seeded dev DB account was also corrected directly, since `upsert_user` only inserts on first creation and never updates an existing record.
- ~~A licensed exercise content/video database~~ `059-back-public-exercise-library` ships real synced content: a `owner_id: None` platform tier on `exercise_library`, `GET /exercise-library/platform`, and a `sync_workoutx_exercise_library.py` script run live against WorkoutX's real API (5 real exercises synced and confirmed; a full ~1,327-exercise sync would cost only ~14 calls). Vendor note: MuscleWiki was tried first but needs a paid tier for direct API access; WorkoutX's free tier works but is contractually scoped to "evaluation and small projects" — revisit before real production scale.
- Video transcoding/thumbnailing/duration inspection on uploaded exercise videos — `047-back-exercise-video-upload` stores the raw uploaded file as-is, by design.
- Exact "days since last activity" per inactive patient — `048-back-practice-dashboard` only returns a yes/no active signal, by design (keeps the query set to simple `distinct` calls, no per-patient last-activity computation).
- `created_at` backfill for patients created before `048-back-practice-dashboard` shipped — they show `created_at=None` and are excluded from "new this month" counts going forward, not retroactively dated.
- ~~Video/file (non-image) chat attachments~~ Stale — `049` was images-only by design at the time, but `054-back-chat-video-file-attachments` later widened both chat-attachment upload endpoints to accept video and PDF too. This bullet was left un-struck by mistake; corrected now.
- Automatic nutrition-goal computation from age/weight/activity level — `049` has the nutritionist enter the four goal numbers directly, same as every other manually-entered `Patient` field.
- `046-back-branding-and-session-logging` closes the real Phase 2 (dynamic per-tenant branding) that a prior session's numbering mix-up skipped, and deepens Phase 3 (training domain) with an exercise library and real logged session details — this now closes out the full TrainerStudio gap-analysis roadmap as originally scoped (Phase 0 multi-tenancy/billing, Phase 1 engagement, Phase 2 branding, Phase 3 training). `047-back-exercise-video-upload`, `048-back-practice-dashboard`, and `049-back-chat-attachments-and-patient-goals` are direct follow-ups from the "Vitta vs. TrainerStudio" parity report, closing out the full "quick wins" batch on the backend side (chat photo attachments, per-patient nutrition goals) alongside the exercise-video and practice-dashboard specs.
- `050-back-per-set-workout-authoring` is a direct follow-up from a much sharper, screenshot-driven audit of TrainerStudio's actual coach app (32 real screens checked against `nutri_pro`'s code, not the marketing site) — closes the single biggest gap that audit surfaced: `WorkoutExercise` was flat (one sets/reps/weight/rest value for the whole exercise), now each set is authored independently with a rep range, weight, RPE, and rest.
- `051-back-patient-contact-and-archive` and `052-back-coach-workout-log-toggle` close out the same screenshot-driven audit's remaining "high impact, contained" tier: `Patient` gains `email`/`phone`, `DELETE /patients/{id}` archives instead of hard-deleting (with a new unarchive path), and nutritionists can now mark a client's exercise complete on their behalf via a new ownership-scoped toggle endpoint mirroring the patient-facing one. `053-back-patient-tags` is the next punch-list item down: `Patient` gains a free-text `tags` list (same shape as `allergies`, no new endpoint) so `nutri_pro` can group/filter the roster. `054-back-chat-video-file-attachments` widens both chat-attachment upload endpoints from images-only to also accept video and PDF — `app/core/storage.py`'s extension map already supported these, only the router-level content-type gate needed unlocking. `055-back-dashboard-patient-growth-trend` adds the practice dashboard's first trend line: `GET /patients/dashboard` now returns `new_patients_by_month` (6 months, chronological), computed the same simple-`count_documents` way as every other dashboard number. `056-back-multi-media-exercises` replaces `WorkoutExerciseIn.video_url` (single URL) with `media: List[WorkoutMediaIn]` (photo or video, multiple), and widens `POST /workout-plans/exercise-media` (renamed from `exercise-videos`) to accept images too, deriving `media_type` from content-type. `057-back-per-set-workout-logging` replaces the flat, delete-then-insert-toggle `workout_logs` shape with a real per-exercise upsert holding a `sets` list (one entry per authored set), and separates the coach's bare `coach_marked_done` flag from the patient's detailed data so the two write paths can no longer clobber each other. `058-back-weekday-workout-scheduling` adds an optional `weekdays: List[int]` (ISO weekday ints) to each authored workout day, validated so no weekday is double-booked across a plan — the first backend concept enabling frontends to surface "today's workout." `059-back-public-exercise-library` gives `exercise_library` a platform tier (`owner_id: None`, mirroring `content_library`'s existing platform/nutritionist split) plus `GET /exercise-library/platform` and a `GET .../video-url` fetch-once-cache-forever resolver, synced live against WorkoutX's real API (switched from MuscleWiki after confirming it needs a paid tier for direct API access). `060-back-medlineplus-content-library` grows the platform article tier from 5 hand-written articles to 110, synced live from MedlinePlus (NIH) across 4 sampled-for-relevance categories (nutrition, wellness, diabetes, exercise) — free, keyless, native Spanish content, zero changes needed to `content_library`'s existing schema/router/frontends since the platform tier already fully supported this. `061-back-public-content-library` adds `GET /content/articles/platform` (mirroring `exercise_library`'s platform-endpoint pattern) so `nutri_pro` can browse that content too — the existing unfiltered `GET /content/articles` couldn't be reused, since it also returns every other nutritionist's private articles. `062-back-workout-log-session-photo` closes the other deferred item from `046`: a patient can now attach a photo to a logged exercise entry, via a dedicated `POST /me/workout-logs/photo` upload endpoint (mirroring `049`'s message-attachment shape) rather than folding multipart handling into the shared `PUT /workout-logs/exercise` upsert. `063-back-article-source-url` adds `source_url` (mirroring `video_url`'s exact shape everywhere, including the separate patient-facing merged serializer in `me`) and captures the real MedlinePlus page URL the sync script was already fetching but discarding — a live re-sync backfilled it onto 105 of the 110 platform articles (the other 5 are hand-curated, with no real external source). `064-back-eating-out-macros` adds `carbs`/`fat` to `EatingOutOption` and `food_diary_entries` (mirroring `036-back-plan-item-macros`'s `PlanMealItem` fields, which eating-out never got) — the smaller half of a fix whose real bug turned out to be client-side: `nutri_app`'s `063-front-eating-out-macro-totals` found that eating-out diary entries weren't counted in the patient's daily macro totals at all, independent of which fields existed. Next steps are user-driven from here.
